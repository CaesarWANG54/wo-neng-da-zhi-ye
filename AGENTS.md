# Mobile Prototype Agent Guide

## Prototype Instructions

In ChatGPT Work Mode, run `sites-preview start "$PWD"`, open `http://terminal.local:4173/` in the cloud browser, and verify the rendered app and its primary interactions. Keep that preview open and tell the user to inspect it in the cloud browser; do not present the local URL as a user-facing chat link. In Codex Desktop, run the local server yourself, open the preview in the in-app browser, and provide the clickable local URL. Do not deploy to Sites unless the user explicitly asks to share, publish, or deploy. Do not give the user server-start instructions when you can run it.

Before planning or implementing any mobile-app change, read this `AGENTS.md` in full. It is the source of truth for the template's runtime and component guidance.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Editing Boundary

- Build app-specific UI in `src/Prototype.tsx` and `src/prototype.css`.
- Treat `src/App.tsx`, `src/main.tsx`, `src/styles.css`, `src/mobile/`, `public/assets/iphone/`, `public/assets/android/`, `public/assets/status/`, `vite.config.ts`, `worker/index.js`, and `scripts/prepare-sites-build.mjs` as protected runtime files. Do not edit, replace, remove, or recreate them unless the user explicitly asks to change the mobile runtime itself. For an explicit runtime change, update the affected lock hashes only after verifying the new runtime behavior.
- Run `npm run check:runtime` before preview or handoff. If it fails, restore the protected runtime instead of weakening or bypassing the check.
- `npm run build` preserves the mobile runtime and prepares the static Cloudflare Worker output required by Sites. Before a Sites handoff, confirm `dist/client/index.html`, `dist/server/index.js`, `dist/.openai/hosting.json`, and source `.openai/hosting.json` exist, then run `npm run test:sites`. Do not replace this project with a Vinext starter.

## Runtime Contract

- Preserve the mobile device runtime unless the user's task explicitly asks otherwise. Do not replace it with a standalone page. Visual fidelity applies to app-owned content inside the device screen, not to template-owned device chrome.
- Keep `App` composed around `PhoneFrame` -> `KeyboardProvider`, with `StatusBar`, app content, `HomeIndicator`, and `KeyboardDock` mounted inside the phone frame. `StatusBar` and the iOS home indicator are overlaid device chrome. When the Android keyboard is closed, the app viewport reserves the protected navigation-bar region instead of painting behind it. When the Android keyboard is open, preserve the current full-screen keyboard layout: its asset includes the IME navigation strip and the separate black navigation bar is hidden. iOS screens continue to paint behind the home-indicator area and own their safe-area content padding.
- Preserve the `iPhone` / `Pixel 10` device picker and both calibrated device presets. The Pixel screen is `427 x 952`; its `32 x 32` camera circle and `public/assets/android/navigation-bar.svg` bottom navigation bar are protected device chrome, not app content.
- Preserve the device picker's intentionally lightweight Codex styling in the top-right corner: its trigger wrapper is borderless and transparent, its trigger sizes to content, and its right-aligned menu uses the compact 3px inset plus the specified hairline and elevation shadow layers. Keep the prototype root and default app screen white.
- Preserve `StatusBar` as live device chrome, including its platform-specific typography, source status-icon assets, and spacing. Pixel 10 uses Roboto, Android indicators, and 32px top, left, and right padding. iPhone uses its iOS indicators, system typography, and calibrated spacing. Do not hardcode screenshot times like `9:41` into the status bar, replace its real-time clock, or move status bar content into app markup unless the user explicitly asks for a fixed/mock device time.
- `PhoneFrame` owns the calibrated device frame, screen portal, device picker, camera cutout, and custom cursor. Keep device assets in `public/assets/iphone/` and `public/assets/android/`; if an asset fails to load, repair the asset path or restore the asset instead of removing the frame, keyboard, or image render.
- Use `MobileScroll` directly for simple single-screen prototypes. Use `FlowStack` for conventional multi-screen flows whose routes can own their fixed header and footer; when using it, define each route as a `FlowScreen`: `{ id, header?, headerHeight?, footer?, footerHeight?, render }`, and use `flow.push(screen)`, `flow.pop()`, and `flow.replace(screen)` from `FlowStack` render callbacks or `useFlow()` instead of introducing another router.
- Use `Carousel` for a carousel, horizontal rail, swipeable cards, image or media strip, horizontally scrollable cards, chip rail, or other horizontal collection.
- For a layered app shell—such as a persistent composer, independently presented sheet, pushed/peek sidebar, or app-wide transition—compose directly in `Prototype.tsx` rather than forcing it through `FlowStack`. Keep app-owned fixed chrome as sibling layers outside `MobileScroll`.
- When using `FlowScreen`, put route-owned fixed headers or footers in `FlowScreen.header` or `FlowScreen.footer`. Set `headerHeight` to the visible app-toolbar height; `FlowStack` adds the device's top safe-area/status-bar inset automatically. Do not include `StatusBar` or its height in the header. Set `footerHeight` to the full app-footer height. `FlowScreen.footer` is an overlay, not reserved layout space; screens using it must add their own bottom content padding such as `padding-bottom: calc(var(--flow-footer-height) + var(--mobile-safe-area-height) + 24px)` so final content can scroll above the footer while still painting behind it.
- Render only scrollable content inside `MobileScroll`; it is for content that should move with scroll and rubber-band overscroll. Keep app-owned headers, nav bars, tabs, composers, and overlays outside it. This keeps scroll physics, safe areas, keyboard insets, scrollbars, and drag click suppression active without letting content paint under fixed chrome.
- Buttons, links, cards, and images inside `MobileScroll` should still allow drag scrolling when the pointer moves beyond tap slop. Use `data-scroll-drag="ignore"` only for rare controls that must own the drag gesture themselves.
- Do not add `var(--keyboard-height)` to ordinary screen/content padding inside `MobileScroll`; the scroll viewport already shrinks above the simulated keyboard. For custom fixed composers, search bars, or toast chrome, use `useKeyboardInsets().bottomInset`. It is relative to the app viewport: Android returns `0` while the closed-keyboard viewport already reserves navigation, then returns the keyboard height while open; iOS continues to clear the home indicator while closed and ride directly above the keyboard while open. Do not pin custom bottom chrome to `bottom: 0` or only `keyboardHeight`.
- Use `KeyboardInput`, `KeyboardTextarea`, or `MobileTextField` for every text-entry control. A raw `input` or `textarea` disconnects focus, keyboard animation, safe-area insets, and attached surfaces.
- Use `BottomSheet` for phone-scoped sheets. Its props are `open`, `onOpenChange`, `title`, optional `description`, optional `snap`, and `children`; it renders through the phone screen portal and dismisses the keyboard before opening.

## Horizontal Carousels

- Use `Carousel` for horizontally draggable cards, images, media, chips, or other horizontal collections. Do not recreate these with `overflow-x`, custom pointer handlers, or a generic div.
- `Carousel` can be nested directly inside `MobileScroll`. It owns horizontal gestures and automatically yields vertical gestures to the parent.
- Never put `data-scroll-drag="ignore"` on or around a `Carousel`; doing so prevents vertical parent scrolling when a gesture begins inside it.
- Do not add CSS scroll snapping to `Carousel`; its runtime owns momentum and release motion.
- Use `data-scroll-drag="ignore"` only when a control must prevent parent scrolling in every drag direction.

See `src/mobile/COMPONENTS.md` for the full component and gesture contract.

## Durable Product Decisions — 我能打职业

- The primary visual reference is retained as local-only design evidence and is intentionally excluded from this public repository pending redistribution review. Preserve the documented warm paper playbook surface, compact top scoreboard, circular pieces with generic jersey numbers, route lines, and dominant full-court board; validate public changes against the rendered app and this textual contract.
- The game is landscape-only inside the protected mobile runtime. Keep both iPhone and Pixel 10 previews working; reserve space for the iPhone camera island, Pixel camera circle, Android navigation bar, and iOS home indicator.
- The action rail belongs on the right and contains exactly five large slots. On-ball labels are 传球、突破、投篮、挡拆、战术. Off-ball and defense contexts may replace labels in the same five slots, but their order and location must remain stable.
- Creation template values 80/79 are rookie signature starts, never a per-template growth cap. All trainable ratings share the global cap of 99.
- A repeated tactic family must change its full execution signature (side, semantic branch, or primary participant). Show only the current next nodes and at most three key role labels; tactic execution must affect outcomes within a bounded ±3 percentage-point window.
- Do not add or restore an expandable special-moves drawer. Double-tap pass for alley-oop and double-tap shoot for dunk are documented only in 玩法说明 and contextual teaching.
- Screen semantics are contextual: on-ball calls a teammate screen; off-ball sets a screen for the real ballhandler. A screen can fail, create drop/hedge/blitz outcomes, or atomically switch matchups. Post-switch actions always read the new defender.
- Use the reviewed runtime court asset in `public/assets/game/paper-court.webp`; its recoverable source and hashes are declared in `public/assets/game/game-asset-manifest.json`. Use the installed icon library for interface icons. Do not approximate visible assets with emoji, text symbols, inline SVG art, or CSS drawings.
- Runtime UI must not contain league names or league/team logos, official uniform graphics, or copied competitor tables. Team short names and representative colors are content data gated by `docs/rights/rights-ledger.md`.
- Prototype source data is synthetic. Licensed real-person ratings must be imported later through a reviewed data adapter with source, version date, confidence, and approval fields; never paste a competitor's proprietary ratings table directly into runtime code.
- Court pieces must visibly move from deterministic match state rather than remain static decorations. AI teammates and opponents follow position-appropriate spacing, matchup, transition, and selected tactic routes; guards organize outside while interior players occupy screen, roll, post, and rim-protection zones.
- The right five action slots express decisions for the single created/controlled player only. Team movement may react through AI, but clicking or inspecting another piece never transfers control. Every enabled slot must change rules state, player intent, movement, matchup, or shot/pass outcome; text-only no-op buttons are not acceptable.
- Mark the controlled player with one thin red circular ring outside the round piece. Do not use a square focus frame as the persistent control marker; inspection/focus styling must remain visually subordinate.
- Keep the help dialog concise: short action rules and double-tap reminders only. Detailed formulas, implementation status, and future mechanics belong in project docs rather than the in-game help surface.
- Match motion uses a 20 Hz presentation cadence with fixed simulation substeps no larger than 50 ms, persistent velocity/acceleration, and one 58 ms linear CSS interpolation shared by pieces, ball, and screen marker. Do not restore long phase-specific 420–900 ms easing or give the ball a different transition duration.
- Use the board's visually scaled court metric for movement, defensive distance, and soft spacing. Ordinary same-team targets keep a 14-unit visual gap; only explicitly declared screen/handoff contact, rebound contests, and legal free-throw lane slots may use reduced gaps. Collision correction never moves the uncommanded created player.
- Tactical route lines are generated from each player's live position and remaining `motion.routes`; hard-coded decorative paths that can disagree with gameplay are not acceptable.
- Dead balls, live-ball possession changes, period boundaries, and final state cancel incompatible routes and velocities atomically. A screen is requested first, locks repeat input while approaching, and only resolves coverage/matchups after its contact timer.
- Pause and background freeze acceptance reads actual rendered bounding boxes as well as logical coordinates. The display must stop within the short interpolation window and must not catch up elapsed hidden time on resume.
- Opponent offense runs only inside the authoritative `advanceMatchTime` loop. It selects from the neutral nine-family catalog, advances one visible semantic stage at a time, exposes a defense-response window, and resolves from actual ratings/matchups without a React timer or hidden rating mutation. Dead ball, possession change, period end, and final clear its token and clock atomically.
- The ordinary user entry point starts at created-player setup rather than directly on the board. Setup includes five positions and 30 original archetype templates (PG7/SG6/SF5/PF6/C6), with the user-requested Chinese player-style reference appended to each label, plus a cyclic `0..99, 00` jersey-number stepper before the UMich/UCoon 60:60 final-three-minute tutorial. The stored value for double zero is the semantic string `"00"`, never numeric `100`; test fixtures may bypass setup only through an explicit `qa` query.
- Tutorial completion presents the one-time first-year choice between a score-derived first-round result and direct selection from the 30 reviewed Chinese short-name teams. Team presentation is a short name plus one flat representative color only; no crest, official uniform art, or logo is permitted.
- The first-year draft uses the reviewed 2026 first-round slot order and 30 English prospect names. Reveal picks sequentially; a player at pick three must see picks one and two first. Insert the created player at the awarded slot, shift subsequent prospects down one, and keep the selecting-team order fixed. Direct signing remains the mutually exclusive alternative.
- The 2026-27 published schedule source contains 1,200 assigned games (80 per team), not a fabricated complete 1,230-game table. Preserve the two Cup-derived TBD entries per team until in-game standings resolve 30 `DYNAMIC_CUP` games. The calendar renders only the created player's team while the simulation advances all 30 teams; simulated games award no action-game coins.
- Career home is a real month calendar, not a seven-day placeholder. Keep coins in the top bar and all 38 ratings in the adjacent scrollable panel. Date clicks select a target and require an explicit second confirmation before simulation; month, next-game, settings, awards, training-selection, and replay controls must all have observable effects.
- Postseason uses the frozen M6B-2 tree: first round `1v8`, `4v5`, `3v6`, `2v7`; no reseeding; every series is best-of-seven with `H-H-A-A-H-A-H`, exactly one legal next game per active series, and one eventual champion. The created player's playoff game may be played or simulated through the same result ledger. Play-in and playoff games never award coins, change chemistry, or write into regular-season player statistics.
- M6B-3 stores created-player postseason performance separately in `PLAY_IN` and `PLAYOFF` buckets. Each bucket owns immutable per-game records and replay-derived 13-field totals. A fresh career must account for every final involving the player's team; migrated saves use explicit `PARTIAL_LEGACY` coverage and legacy game IDs instead of inventing missing player lines. Root career saves use schema v4 with in-memory v1/v2/v3 migration and cross-check season, progression, lifecycle, postseason tree, performance records, and compact history.
- A career season settles only after all 1,230 regular-season games, the exact season award set, a valid frozen postseason tree, one champion, and its unique season-completion event are present. Settlement archives a compact summary, advances age once, applies the deterministic new-age decline budget, then persists a notification that must be acknowledged before the next season. Replays are `NOOP`; mismatched event/history states are rejected.
- The created player begins at age 20. Ages through 31 receive no fixed age decline; `31→32` is the first decline. M6B-3 uses no hidden experience protection or random skill increase. `39→40` forces retirement exactly once, keeps the final playable season at 20, and never creates season 21. League retirement notices are synthetic by default; named real-person retirement content may enter only through the separate `rightsStatus === "APPROVED"` hook.
- Season 1 retains the reviewed 2026–27 schedule snapshot. Seasons 2–20 use deterministic project-generated schedules labeled `PROJECTED`/“项目生成赛程”; never describe them as published or current real schedules. Each season still resolves 1,200 base games plus 30 in-game Cup games, resets current-season results/statistics/awards/postseason and training-inactivity cadence, preserves permanent ratings/economy/history, and omits rookie awards after season 1.
- M6B-3 is formally green at the 2026-09-03 D-drive checkpoint: runtime integrity 28 protected files, core 27 files/374 tests, desktop runtime 98 passed with 9 intentionally skipped, native WebKit 18/18 across iPhone 13 844×390 and iPhone 15 Pro 852×393, and production build/content gates passed. This closes only the M6B-3 scope; physical-device Safari remains an M9 gate, and real-person retirement content remains blocked unless independently approved.
- Ball presentation uses a real flight state. Convert board x/y percentages independently against a 28.65m by 15.24m court, derive duration from metric distance and pass-speed rating, advance it in the same 50ms authoritative loop, and keep the shared 58ms CSS interpolation. Do not replace it with a fixed-duration jump to the new handler.
- Backcourt advancement finishes only when the live handler position actually crosses the center line; the eight-second clock remains authoritative until then. Once frontcourt control is established, a later offensive catch/control in the backcourt is a distinct over-and-back turnover, not an eight-second violation; scripted AI receivers must cross first rather than manufacture a violation. An ordinary defensive deflection out of bounds with the offense retaining possession keeps the unused shot-clock time. Apply a 14-second frontcourt value only to the separately tagged rule cases that require it, including a rim-contact rebound/retention path; never restore a blanket `max(current shot clock, 14)` rule for every defensive touch-out.
- Ball presentation is three-dimensional even though the board is top-down: keep ground-plane `x/y`, physical height `z`, and the ground shadow independent. `SHOT_FLIGHT`, `REBOUND`, `RIM_REBOUND`, `LOOSE_BALL`, and `OUTLET` are authoritative match/flight states; do not fake height by shifting court `y` or settle a shot/rebound synchronously at button press.
- A missed shot that contacts the rim has no team control until the rebound flight finishes. Resolve all ten players with the same seeded candidate model: landing-point distance and arrival time dominate, followed by the correct offensive/defensive rebound rating, box-out edge, strength, vertical, hands, basketball IQ, speed, and acceleration. Do not add hidden user/AI, home/away, or automatic defensive-rebound bonuses.
- A rim-contact offensive rebound establishes a 14-second second-chance possession; a defensive rebound establishes a new 24-second possession. An airball or blocked-shot loose ball recovered by the offense keeps the elapsed shot clock. The referee state machine models shooting and ordinary personal fouls, team-penalty free throws, automatic one/two/three-shot sequences, live last-miss free-throw rebounding, offensive and defensive three seconds, defensive goaltending, offensive basket interference, eight-second advancement, and established-control over-and-back violations. It does not yet model tips, repeated rebound taps, rebound fouls, jump balls, substitutions, coach challenges, team timeout inventory, the full family of free-throw lane violations, or arbitrary user-initiated airborne touches; documentation must preserve those boundaries and must not claim full professional-rule coverage.
- During `FREE_THROW`, game and shot clocks freeze, every right-rail action is unavailable, only the designated shooter is visually marked as the free-throw actor, and the created-player control ring remains on the created player. The shooter and the other nine pieces animate into the legal lane/perimeter formation; the release and result are automatic, and the last missed attempt enters the shared ten-player rebound flow.
- The authoritative box-score ledger always contains exactly five home and five away players. Actual events—not team placeholders—own makes/attempts, threes, free throws, points, offensive/defensive rebounds, assists, steals, blocks, turnovers, personal fouls, playing time, and plus-minus. The scoreboard point delta must equal the ten-player point delta and total plus-minus must remain zero.
- Natural personal fouls are intentionally sparse and symmetric for the user and computer. Count a new offensive possession only when team control changes, plus the first possession of a new period; offensive rebounds, defensive deflections out with offense retaining, and ordinary-foul continuations stay in the same possession slot. In every sliding 10-possession window there may be at most one natural personal foul, and in every sliding 50-possession window at most one natural three-point shooting foul. The fifth consecutive steal click in one defensive possession and a trailing AI team's deterministic late-game intentional foul are explicit user/strategy fouls: they use the normal personal/team-foul and Bonus chain but do not consume or bypass future natural-cadence history.
- The created player has a stable `createdPlayerId`, remains the single controlled player, and is never removed by ordinary rotation. The current prototype has a fixed ten-player on-court roster and no substitution engine; even a recorded sixth foul only enters the disqualification ledger and does not remove the created-player piece. Any future rotation selector must explicitly exclude `createdPlayerId` from normal substitution candidates unless this product decision is changed.
- After a defensive rebound, choose between self-push and a visible outlet from actual handling, basketball IQ, ball security, hands, pass accuracy/vision, receiver pressure, distance, and transition progress. An outlet may be intercepted; otherwise the selected handler must physically cross midcourt under the same eight-second rule before frontcourt offense begins.
- Every submitted right-rail defense response must leave immediate button-level and board-note feedback. Opponent route signatures combine play, side, and one of three deterministic geometry variants and cannot repeat identically on consecutive starts.
- Treat the entire prototype as a no-silent-click surface: every enabled button must produce an observable route, modal, selection, rule-state, intent, movement, matchup, ball/shot result, or explicit rejection reason. Temporarily unavailable game actions must be disabled and show the current lock reason; help return buttons must restore their actual caller, and restoring the tutorial checkpoint closes pause and returns to the reset board.
- Pass and shoot share one global 260ms tap-arbitration slot. A second tap of the same action forms its documented double action; a different action inside the window replaces the older pending tap, so only the latest choice resolves. Never keep parallel pending timers that can cancel or swallow a later input, and show the pending choice immediately both on its button and in the board note.
- Match audio uses bundled, same-origin, manifest-and-SHA-256-verified MP3 assets only. A low-volume dribble loop may play in live phases after the first user gesture; pause, hidden/background state, dead ball, inbound preparation, free throws, period breaks, tip-off setup, mute, and final state stop it immediately. A swish cue is reserved for actual made field goals and made free throws, never awarded goaltending points. Do not add remote media URLs or bypass `public/assets/audio/audio-manifest.json` and the postbuild content gate.
- A drive is a live, interruptible basketball action rather than an instant random roll. Read actual defender positions when the drive begins: an empty rim starts one visible route and auto-finishes as a dunk only after the handler reaches a credible near-rim release point; a set defense keeps the layup/finishing calculation against the primary defender and any live-position rim helper. While the drive is active, one pass tap resolves immediately as a drive-and-kick to the nearest legal perimeter teammate, cancels the old finish route, and still reads pass security and interception risk. Never count a distant big as phantom rim protection or launch a dunk flight from the perimeter.

## Keyboard Rule

The simulated keyboard is a separate top-layer component. Before presenting anything that behaves like iOS navigation or modal UI, dismiss it first.

Call `keyboard.hide()` before:

- pushing, popping, or replacing FlowStack routes
- opening bottom sheets, action sheets, dialogs, menus, or navigation sheets
- starting transitions where the destination should not inherit text-input focus

`FlowStack` already hides the keyboard for `push`, `pop`, and `replace`. `BottomSheet` already hides it before opening. If you add new modal/sheet/navigation primitives, follow the same rule.

When a composer, search surface, or other keyboard-attached component closes, call `keyboard.hide()` in the same event before changing that component's open state. Position attached surfaces from `useKeyboardInsets()` rather than a separate timer or visibility flag so both dismiss together.

When any text-entry control loses focus, dismiss the simulated keyboard. If the control is custom or does not use the runtime's keyboard-aware fields, handle its blur event and call `keyboard.hide()` explicitly. Keep the keyboard open only when focus is moving directly to another text-entry control that should share the same keyboard session.

## Interaction Rules

- Do not trigger buttons or inputs after a pointer has become a drag. Preserve the drag suppression behavior in `MobileScroll`.
- Do not allow native browser image/file dragging inside the phone frame. Preserve the phone-level `dragstart` suppression and non-draggable image styles so scroll drags that begin on images still scroll the prototype.
- Use `KeyboardInput`, `KeyboardTextarea`, or `MobileTextField` for text entry so the simulated keyboard and safe-area insets stay connected.
- Fixed phone chrome should not animate with pushed screens. Screen content can animate; the status bar, camera cutout, and preview chrome should stay put.
- Keep the keyboard below the home indicator/safe area layer in z-index, and above ordinary app UI while visible.
- Keep the home indicator as the topmost safe-area layer in the z-index above everything else in the prototype.
