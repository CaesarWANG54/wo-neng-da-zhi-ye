# M6B-3 季后赛个人统计、季末结算与跨赛季循环规则决策（冻结）

日期：2026-09-03
范围：附加赛与季后赛个人统计、季末年龄与衰退、退役通知、40 岁强制退役、下一赛季循环和根存档 v4；不包含真人阵容、合同/转会、伤病、长期体能、未来真实赛程导入或最近五场模拟校准。

## 1. 阶段目标与既有边界

- M6B-3 只在 M6B-2 已产生唯一总冠军后闭合赛季。不得改写固定季后赛树、七局四胜、`H-H-A-A-H-A-H`、比分事件或既有晋级结果。
- 附加赛和季后赛继续不发金币、不改变球队默契、不消耗训练次数，也不回写常规赛 `PlayerSeasonLine` 或常规赛奖项口径。
- 季后赛个人统计、季末结算和下一赛季都必须由可重放、可序列化的纯领域状态驱动；React 只负责展示和提交意图。
- 同一操作的双击、刷新重放、存储重试或重复事件只能得到 `NOOP`，不得重复累计统计、涨龄、衰退、生成通知、归档赛季或创建下一赛季。

## 2. 季后赛个人统计口径

### 2.1 独立统计桶

- 创建球员的季后赛数据与常规赛完全分离，并拆成两个独立桶：
  1. `PLAY_IN`：附加赛；
  2. `PLAYOFF`：首轮至总决赛。
- 每个桶同时保存逐场账本和由逐场账本推导的合计。合计不能作为第二份可任意修改的事实；加载时必须由逐场账本重放并交叉校验。
- 逐场记录和合计使用同一套 13 字段：
  - `games`
  - `points`
  - `rebounds`
  - `assists`
  - `steals`
  - `blocks`
  - `turnovers`
  - `made`
  - `attempts`
  - `threesMade`
  - `threesAttempted`
  - `freeThrowsMade`
  - `freeThrowsAttempted`
- 单场记录的 `games` 固定为 `1`；空桶合计的 13 项均为 `0`。不得把未知旧档统计伪装成空桶。

### 2.2 手打与模拟一致性

- 只有创建球员所属球队的已结束比赛生成个人统计记录；模拟其他球队比赛只更新比分和晋级，不生成创建球员统计。
- 手打比赛从终场十人技术统计账本读取创建球员行，转换为上述 13 字段；不得从比分或界面文本反推。
- 模拟创建球员所属球队的比赛使用同一 13 字段结构、同一合法性检查和基于 `seasonNumber + gameId + 比赛事件ID` 的确定性种子。相同存档重放必须产生相同统计。
- 模拟与手打都必须满足：全部字段为非负安全整数；命中数不超过出手数；三分命中不超过三分出手和总命中；三分出手不超过总出手；罚球命中不超过罚球出手；由投篮与罚球推导的得分等于 `points`；球员得分不超过本队得分。
- 每个创建球员所属球队的已记录比赛最多有一条个人统计记录，并通过 `gameId`、原比分事件 ID、统计事件 ID、来源 `PLAYED | SIMULATED` 和阶段桶关联。相同内容重放为 `NOOP`；不同统计、不同比分来源、越序或陈旧 revision 必须拒绝且不改变任何状态。
- 玩家球队被淘汰后，继续模拟联盟剩余比赛不得改变其任何季后赛个人统计。

### 2.3 奖励与奖项边界

- `PLAY_IN` 与 `PLAYOFF` 均为零金币、零默契变化、零训练额度变化；夺冠在本阶段只形成荣誉和赛季摘要，不附加隐藏经济奖励。
- 常规赛统计、常规赛奖励事件、常规赛奖项和首年新秀奖评选均不得读取季后赛个人统计。
- 季后赛界面可以展示附加赛、正式季后赛及两者合并的只读合计；合并合计仍由两个桶的逐场账本计算，不能写回常规赛。

## 3. 旧档统计覆盖范围

- 根存档 v3 没有季后赛个人统计，迁移时统一标记为 `LEGACY_UNKNOWN`；不得根据球队比分虚构球员数据，也不得把未知显示为 0 场、0 分。
- v3 迁移后的新比赛可以正常写入逐场账本，但界面必须把合计标为“迁移后已记录部分”，不能宣称是完整季后赛总计。
- 统计覆盖状态、追踪起始 revision 和已记录事件必须持久化。刷新、导入或再次迁移不得把 `LEGACY_UNKNOWN` 自动升级为完整覆盖。
- 全新 v4 生涯从附加赛第一场开始使用 `COMPLETE` 覆盖；验证器要求每场创建球员所属球队的已结束比赛与统计账本一一对应。

## 4. 季末结算门禁与固定顺序

季末结算只在以下条件全部满足时开放：

1. 常规赛 1,230 场均为 `FINAL`，动态杯赛已解析；
2. 常规赛奖项已经生成且通过校验；
3. `postseason.playoffs.status === COMPLETE`；
4. 唯一 `championTeamId` 已存在；
5. `seasonCompletionEventId` 已存在，属于当前季后赛事件账本，并与当前冻结事件及冠军链一致。

创建球员球队无缘季后赛或已被淘汰都不构成赛季完成；玩家必须继续模拟到联盟总冠军产生。门禁未满足时返回明确的 `NOT_READY`，不改变根 revision。

满足门禁后，状态机严格按以下顺序推进并逐步持久化：

1. **冠军锁定**：读取已存在的唯一冠军及 `seasonCompletionEventId`，不重新计算系列赛。
2. **赛季摘要**：生成当前赛季不可变紧凑摘要。
3. **年龄与衰退**：年龄 `+1`，按新赛季年龄执行一次确定性预算衰退。
4. **退役通知**：生成并持久化本季通知，必须由玩家确认。
5. **下一去向**：未满 40 岁则在确认后创建下一赛季；达到 40 岁则进入生涯结束状态。

年龄与衰退已经结算但通知尚未确认时，刷新必须恢复到同一通知，而不是重复结算或跳过通知。写盘失败必须留在原界面，任何阶段都不得只在内存里先行提交。

## 5. 年龄与衰退

- 创建球员 20 岁开始。常规赛结束、奖项生成或玩家球队被淘汰时都不涨龄；只有第 4 节所述季末门禁通过后才涨龄。
- 年龄预算读取结算后的新年龄，因此 `31 → 32` 是第一次固定年龄衰退。
- 当前冻结预算如下，数字表示该类别当季总扣点预算：

| 新赛季年龄 | 运动能力 | 终结与防守执行 | 投篮/控传/篮球智商 |
|---|---:|---:|---:|
| 20–31 | 0 | 0 | 0 |
| 32 | 1 | 0 | 0 |
| 33–34 | 1 | 1 | 0 |
| 35 | 2 | 1 | 0 |
| 36 | 2 | 1 | 1 |
| 37 | 3 | 1 | 1 |
| 38 | 3 | 2 | 1 |
| 39 | 4 | 2 | 2 |
| 40 | 强制退役，不创建可比赛赛季 | 强制退役 | 强制退役 |

- 预算沿用当前确定性分配：只从该类别中高于 25 的能力候选选取，按当前永久值排序后使用赛季、年龄和类别组成的稳定轮转；每次账本条目只扣 `1`，所有结果保持 `25..99`。
- M6B-3 不启用隐藏的“经验保护”、随机技术不降或低概率技术 `+1`。领域函数即使保留扩展参数，正式季末事务也必须传入空保护集。若未来加入选择式保护，必须另立规则版本、UI 和迁移，不得静默改变旧档结果。
- 伤病、耐久、出场时间、球员风格和长期体能尚未成为年龄预算输入；文档不得宣称当前衰退已经读取这些尚未实现的系统。
- 年龄衰退与训练荒衰退使用不同来源和事件 ID。每一点变化继续写入完整成长账本，包含赛季、周、年龄、能力、前值、变化、后值和中文原因。

## 6. 赛季边界的保留与重置

季末年龄结算后保留：

- 创建球员身份、位置、模板、号码、初始新秀基线和原始去向；
- 衰退后的永久 38 项能力；
- 金币、球队默契；
- 已获得的副属性 50/100 进度 `secondaryProgressUnits`；
- 完整成长账本和全部已处理事件 ID；
- 难度、音量、比赛时长等共享设置。

新赛季开始前重置：

- `week = 1`；
- `sessionsUsedThisWeek = 0`；
- `trainedGroupsThisWeek = []`；
- 所有训练组 `groupDormancyWeeks = 0`；
- `inactivityProgressUnits = {}`；
- `seasonInactivityLosses = {}`；
- 新赛季常规赛比分、战绩、创建球员常规赛统计、奖项和季后赛活动状态。

离季期间不自动触发训练荒扣点。重置训练荒计数不能删除已发生的历史扣点或成长账本。

## 7. 退役通知与 40 岁强制退役

- `39 → 40` 只处理一次：年龄变为 40、`retired = true`，生成创建球员退役通知并结束生涯；不创建可操作的第 21 个赛季，也不显示空的“赛季 21”日历。
- 退役通知在冠军、赛季摘要和年龄结算之后出现，在下一赛季或生涯结束之前确认。通知及确认事件都必须持久化和幂等。
- 退役后不能开始或模拟比赛、训练、购买属性、领取奖励或改变默契。界面只提供查看生涯摘要和新建独立生涯等不会修改已退役档案的操作。
- 当前没有完整真人阵容，因此联盟退役公告默认使用原创合成姓名和确定性规则生成。不得伪装成现实退役名单。
- 真人姓名、音译名、昵称或指定剧情退役只能通过独立内容钩子进入；仅 `rightsStatus === APPROVED` 的内容项可以显示和归档。`REVIEW`、`BLOCKED`、仅开发参照或缺少人物范围许可的项目必须过滤。
- 指定真人退役剧情不得写进通用年龄公式，不得因内容项被过滤而影响创建球员的季末结算。

## 8. 下一赛季与未来赛程

- 第 1 年继续使用已经审定的 2026–27 数据快照。第 2 年及以后使用项目原创的确定性未来赛程生成器，并明确标记为 `GENERATED_FUTURE`；界面和文档不得声称这些赛程与现实同步或属于官方发布。
- 每个生成赛季必须有独立 `seasonNumber`、起止日期、杯赛解析日期、`scheduleRulesVersion`、确定性种子和来源标签。
- 每个赛季仍包含 30 支球队、每队 82 场、联盟合计 1,230 场；其中 1,200 场在赛季壳创建时确定，30 场沿用动态杯赛解析语义。不得出现球队自赛、重复场次 ID、赛季外日期或不平衡的球队场次数。
- 所有比赛、训练周、奖励、默契、排名冻结、附加赛、系列赛、统计、季末和通知事件 ID 都必须包含 `seasonNumber` 或等价的不可碰撞赛季命名空间。不得清空历史已处理 ID 来规避跨年冲突。
- 新赛季从新的常规赛日历开始，`postseason` 为空；上一季季后赛只能通过历史摘要查看，不能继续操作。
- 第 2 年起不再出现创建、教学、选秀仪式、直接选队、最佳新秀或最佳新秀阵容。常规奖项继续按当前赛季常规赛数据生成。
- 当前没有合同、自由市场或交易系统，创建球员在下一赛季继续效力原球队；这只是 M6B-3 范围边界，不代表未来永久禁止转队。

## 9. 紧凑赛季历史

- 每个完成赛季只归档紧凑摘要，不保留整份 1,230 场赛程副本，避免 20 年生涯使存档线性膨胀到不可控大小。
- 摘要至少包含：赛季编号与日期范围、球队与战绩、创建球员年龄区间、常规赛 13 项合计、常规赛奖项、季后赛统计覆盖状态及两个桶的合计、球队季后赛最终轮次、分区冠军、总冠军、`seasonCompletionEventId`、年龄衰退账本范围和退役通知引用。
- 摘要身份由当前赛季编号与 `seasonCompletionEventId` 唯一确定。同一赛季最多一条；不同内容重复归档必须拒绝。
- 历史摘要是只读展示数据。它不能重新发币、修改能力、重算旧奖项或重新打开已结束的系列赛。

## 10. 根存档 v4 与迁移

- `CareerSaveEnvelope.schemaVersion` 从 3 升到 4；localStorage key 继续使用稳定命名空间 `wo-neng-da-zhi-ye:career:v1`，不得随 schema 改名。
- v4 新增独立季后赛个人统计状态、赛季编号/日期描述、紧凑历史和可恢复的季末过渡状态。季后赛比赛树可继续保持 M6B-2 的独立规则版本，不能因新增统计改写历史比分事件。
- 根 v1、v2、v3 都必须只在内存中迁移为 v4；迁移不得增加比赛 revision、重抽排名、重算系列赛、自动涨龄、自动生成下一季或自动确认通知。
- v3 的季后赛统计覆盖必须按第 3 节标记为 `LEGACY_UNKNOWN`，即使旧档已经夺冠也不得回填猜测数据。
- 迁移后的 `profile.age` 仍代表创建时年龄 20；当前年龄的唯一权威是成长状态和季末过渡状态。验证器必须防止二者与活动赛季编号产生不可能的组合。
- 损坏的统计关联、重复赛季摘要、年龄/赛季漂移、缺失冠军完成事件、非法通知内容或跨年事件 ID 冲突进入 `RECOVERY_REQUIRED`，不得静默修复或覆盖。
- 未来根 v5+ 只读拒绝并保持原始存档；存储失败不得用默认新生涯替换用户档案。

## 11. UI 与操作契约

- 季后赛中心新增创建球员统计摘要，明确区分“附加赛”“季后赛”“合计”，并显示完整、迁移后部分或旧档未知覆盖状态。
- 唯一总冠军产生后显示“赛季总结”入口。按钮只有在第 4 节门禁满足时可用；不可用时显示缺少的具体条件。
- 季末流程依次展示冠军与个人摘要、年龄和逐项衰退、联盟退役通知，再进入“开始下一赛季”或“生涯结束”。每个启用按钮都必须提交真实状态或给出明确拒绝原因。
- 季末结算和通知写盘期间锁定重复输入；写盘失败保留当前弹窗和可重试按钮，不提前切换日历。
- 桌面和 844×390、852×393 iPhone 横屏都必须无页面级溢出；主要按钮触控区域至少 44px，长统计/通知列表在面板内部滚动。
